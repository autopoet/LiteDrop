# CodeDrop 学习指南

这份指南不是另一份需求文档，而是代码阅读路线。目标是让你能回答“为什么这样写”，而不只是把项目运行起来。

## 学习方法

每学一个模块都做四件事：

1. 先说清输入、输出和失败情况。
2. 再读路由与 Schema，确认 HTTP 契约。
3. 跟进 Service 和 Model，画出数据变化。
4. 运行对应测试，再主动改坏一处观察失败。

不要一开始逐行阅读整个项目，也不要背代码。先理解一条完整业务链，再看边界处理。

## 1. 先跑通最小请求

从应用入口、配置和 `/health` 开始。

需要理解：

- FastAPI 应用在哪里创建，路由如何注册。
- 环境变量如何变成带类型的配置。
- 为什么生产配置不合法时要在启动阶段直接失败。
- 应用启动和关闭时，Peewee 连接如何处理。
- 为什么 Peewee 路由使用普通 `def` 而不是强行包装成异步。

动手练习：

```bash
curl http://localhost/health
```

把数据库路径临时改成不可写目录，观察健康检查如何失败。完成后恢复配置。

面试自测：

> Peewee 是同步 ORM，FastAPI 会把同步路由放在线程池执行。SQLite 即使换成异步驱动仍只有一个写入者，所以本项目优先选择简单、可解释的同步方案。

## 2. 理解三张核心表

按以下顺序阅读模型：

1. `UploadSession`：一次未完成或已完成的上传。
2. `UploadPart`：某个会话已接收的分片。
3. `ShareFile`：合并完成后可领取的文件。

自己画出关系：

```text
UploadSession 1 ── N UploadPart
UploadSession 1 ── 0..1 ShareFile
```

重点观察：

- `(upload_id, part_number)` 为什么必须唯一。
- 文件大小为什么使用整数，而不是浮点数。
- 为什么数据库只保存相对路径。
- `uploading → merging → completed/failed` 状态如何限制非法操作。
- SQLite WAL、`busy_timeout` 和短事务分别解决什么问题。

练习：创建上传会话后直接查看 SQLite 中的记录，不上传分片就请求完成，确认状态和错误是否符合预期。

## 3. 初始化上传

初始化接口只创建会话，不接收文件正文。

按这个顺序跟代码：

```text
HTTP 请求
  → Pydantic 参数校验
  → 文件名与业务限制校验
  → 配额和磁盘空间检查
  → 计算 total_chunks
  → 创建 UploadSession
```

必须能解释：

- 为什么 200 MiB 上限既要前端检查，也要服务端检查。
- 为什么初始化时需要预留约两倍文件空间。
- `ceil(total_size / chunk_size)` 如何处理最后一个分片。
- 为什么单文件上限和全局 5 GiB 配额不是一回事。

练习：分别提交 0 字节、200 MiB 和超过 200 MiB 的声明大小，记录返回结果。

## 4. 上传一个分片

这是项目最重要的代码路径之一。

一次正确的分片写入应当是：

```text
校验会话和序号
  → 检查是否已存在
  → 流式写入 .tmp，同时计算 SHA-256
  → 校验实际大小和哈希
  → os.replace 原子改名
  → 最后写入 UploadPart
```

顺序不能随意交换：

- 先写数据库再写磁盘，会留下“数据库说存在、磁盘却没有”的假记录。
- 直接写正式分片名，中途断线会留下看起来完整的损坏文件。
- 一次性 `read()` 整个请求会让并发分片快速吃满内存。

幂等规则：

- 同一编号、相同 SHA-256：直接返回成功。
- 同一编号、不同 SHA-256：返回冲突，不能悄悄覆盖。

练习：

1. 同一分片上传两次，确认只有一条记录。
2. 用相同编号上传不同内容，确认收到 `409`。
3. 修改请求中的 SHA-256，确认临时文件没有被当作正式分片保存。

## 5. 断点续传

断点续传并不是“继续一个 HTTP 请求”，而是重新查询服务器状态后，只上传缺失分片。

```text
浏览器保存 upload_id
  → 页面刷新
  → GET 上传状态
  → 服务端返回 uploaded_parts
  → 前端计算 missing_parts
  → 最多并发上传 3 个
```

需要区分：

- 暂停：不再发起新分片请求，服务器数据保留。
- 取消：调用删除接口，服务器清除会话和分片。
- 失败重试：仅重试当前分片，最多三次。
- 会话过期：两小时后不能继续，由清理任务回收。

练习：上传一半后刷新页面，在浏览器开发者工具中确认已成功的分片没有再次传输。

## 6. 合并分片

合并流程要同时保证状态、磁盘文件和数据库记录的一致性。

```text
短事务：uploading → merging
  → 离开事务
  → 检查全部分片
  → 逐块复制到 .merge.tmp 并计算最终 SHA-256
  → os.replace 为正式文件
  → 短事务：创建 ShareFile，状态改为 completed
  → 清理分片
```

最关键的问题：

> 为什么不能在数据库事务中合并 200 MiB 文件？

因为文件复制可能持续很久。SQLite 同时只有一个写入者，长事务会让其他写请求持续等待。正确做法是用短事务抢占状态，再在事务外执行耗时 I/O。

练习：

- 缺少中间分片时请求完成，确认系统拒绝合并并允许补传。
- 完成接口调用两次，确认返回同一个分享结果而不是生成两份文件。
- 对比原文件和下载文件的 SHA-256。
- 构造一个遗留的 `merging` 会话，重启应用并观察它如何恢复为 `failed`。

## 7. 取件与下载

下载分为两个动作：

1. 使用取件码查询元数据。
2. 原子消耗一次下载次数并签发短期下载凭证。

真正传输文件时使用下载凭证。这样浏览器发起多个 HTTP Range 请求时，不会被重复计算为多次领取。

重点理解条件更新：

```sql
UPDATE share_file
SET download_count = download_count + 1
WHERE id = ?
  AND download_count < download_limit;
```

受影响行数为 1 才能签发凭证。相比“先查询次数，再在 Python 中加一”，条件更新不会让两个并发请求同时拿到最后一次机会。

练习：把限制设为 1，同时发送两次凭证请求，确认只有一个成功。然后使用成功凭证发起多个 Range 请求，确认次数不会继续增加。

## 8. 过期清理

清理任务主要做以下工作：

- 删除超过两小时的未完成会话及其分片。
- 删除过期分享的正式文件和数据库记录。
- 补偿清理“已完成但分片尚未删除”的中断现场。
- 删除超过安全宽限期、且没有数据库记录引用的孤立文件。

清理代码应当允许重复执行：文件已经不存在时不报致命错误，数据库记录已经删除时也不影响下一项。

需要理解：

- 为什么当前项目只运行一个 Uvicorn worker。
- 为什么多 worker 会启动多份进程内定时任务。
- 删除磁盘文件与数据库记录的顺序发生异常时，下一次清理如何恢复。

练习：在测试数据库中构造过期时间，手动触发清理并检查磁盘和数据库。

## 9. 前端上传状态机

前端不是业务规则的最终裁判，它负责把服务器能力组织成清晰交互。

重点状态：

```text
idle → selected → initializing → uploading
                                  ↕
                         pausing → paused
uploading → merging → completed
          ↘ failed
```

阅读时关注：

- 为什么上传进度来自已完成字节数，而不是“请求数量”。
- 三个并发任务如何领取下一个缺失分片。
- 暂停后为什么不强制中断已经快完成的请求。
- 为什么只有在途 worker 全部收尾后才允许继续。
- `localStorage` 保存了什么，为什么不能保存 `File` 对象本身。
- 服务端报错后，界面是否告诉用户下一步该做什么。

练习：在浏览器中模拟慢速网络，暂停、刷新、恢复，再检查请求列表。

## 10. Docker 与 Caddy

最后再看部署，因为它只是把已经理解的程序组合起来：

```text
Caddy
  ├── /api、/health、/docs → backend:8000
  └── 其他路径              → frontend
```

`data/` 保存 SQLite，`storage/` 保存分片和正式文件；它们都挂载到宿主机，因此重建容器不会丢失业务数据。Caddy 的证书数据也需要持久化。

需要理解：

- 为什么只对外开放 Caddy。
- 为什么反向代理只允许约 7 MB 的单次分片请求，而不是 200 MiB。
- 为什么生产环境必须使用域名、HTTPS 和上传口令。
- 为什么 `docker compose down` 与删除持久化数据不是一回事。

| 天数 | 内容 | 当天产出 |

| 1 | 配置、入口、健康检查、模型 | 画出模块和表关系 |

上传、取件和下载链路。V2 各模块的拆分理由见
[V2 设计说明](V2_DESIGN.md)。

## 最终自测问题

如果以下问题不能脱离代码回答，就回到对应章节再做一次实验：

1. 分片上传为什么不等于上传速度一定更快？
2. 最后一个分片的正确大小怎样计算？
3. 为什么分片先落盘，成功后才写数据库记录？
4. 相同编号的分片重复到达时如何处理？
5. 合并失败后怎样避免生成半个正式文件？
6. 为什么合并文件不能处于 SQLite 写事务中？
7. 为什么下载要先签发凭证再传输文件？
8. 条件更新怎样避免最后一次下载被超额领取？
9. 为什么当前版本限制为单 worker？
10. 200 MiB 单文件上限和 5 GiB 全局配额分别保护什么？
